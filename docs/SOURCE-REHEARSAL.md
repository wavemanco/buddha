# Rehearsing the first source experiment

This is an engineering check of the [proposed source experiment](SOURCE-EXPERIMENT.md).
It uses its actual configuration and isolated Python workers, with simulated
provider replies. It spends no API money, reads no real API key and does not
allocate the proposed live budget. [PLAN.md](PLAN.md) owns the roadmap.

The distinction matters: the workers, inherited files, official NoveltyBench 1.1
commands, saved records and continuation controller are real. The model replies
and their usage counters are supplied test inputs. This cannot establish that a
model can write the children or that the children improve useful diversity.

## What the check exercises

The starter is the exact 13,452-byte composition already documented in
[SOURCE-SEED.md](SOURCE-SEED.md). Three supplied children change its generation
procedure while retaining its improvement function literally. Later proposals
must run the selected child's own file and receive the actual measured feedback;
the host does not restore a missing improvement function.

The unchanged proposed schedule contains three development tasks, ten answer
positions per task and three latest-parent iterations. If every supplied child
passes its screen, the resulting four screens and three proposal stages use
51 original stage owners. Those owners identify accounting and evidence; they
are not a promise of 51 API requests.

The controlled generation recipes use 10, 11, 11 and 12 callbacks per task.
Their extra callbacks exercise planning and answer selection. Supplied singleton
partitions create ten quality-scoring heads per assessment, including for tasks
with a restricted legal answer space. These are deliberate transport inputs,
not semantic judgments. This particular success schedule therefore expects
132 generation, three proposal, twelve grouping and 120 quality replies:
267 simulated replies in all. Real model behavior, grouping, retries, rejection
and fallback can produce different counts.

Generation replies are traceable marker strings, not task-compliant stories,
glass descriptions or password digits. They let the check verify callback
history, literal answer retention and reordered/selected answer positions.
Their supplied scores support no claim about task quality or meaningful variety.

The check records actual input-pin counts, source and feedback sizes, request
and frame bytes, cumulative worker output, artifact/storage sizes and elapsed
times. Individual request limits and total worker/storage limits are different
bounds. Passing this finite schedule does not establish that every permitted
future source file, feedback packet or request fits all of them together.

## Interruption and repetition

The check deliberately interrupts after the first iteration's decision has
actually been saved. It retains that cancellation and continues through the
same approved synthetic launch and original owners. Completed prefix records
must remain unchanged; subsequent stages must use their planned original-owner
paths. Newly created owners receive their own recorded IDs.

After completion, it repeats the completed launch in the same host process,
with key access, API sends, worker execution and database writers forbidden.
The launcher must recognize the saved complete report and return a completion
receipt without changing the search records or authorization bytes. The driver
compares the full fixture's bytes before and after this repeat. It records the
comparison's outcome, but does not save those two file inventories separately;
a later reader cannot independently reconstruct that historical comparison.
This checks a durable decision boundary; it is not an interrupted, uncertain
network request or permission to replace one.

## Running and reading it

No command is required from the user for this rehearsal. Its developer entry
point is [the pinned probe](conformance/src02-full-rehearsal.py). Running it
creates a new synthetic fixture, starts local Docker workers, records an
intentional interruption, resumes once and saves a separate result receipt.
It runs once in its current terminal and spends no API money. Ctrl+C stops the
host process; retain the fixture and receipts for inspection.

The recorded configuration uses Python 3.13 on Windows and the pinned Docker
Desktop Linux engine and images from the proposal. Changed local paths or
runtime selections require a newly reviewed bundle and source pins. The
portable guard tests run separately from this concrete Docker schedule.

To display the required developer arguments without starting a rehearsal:

```powershell
python -I -B docs/conformance/src02-full-rehearsal.py --help
```

This prints help once and exits. It needs no separate window, creates no run,
reads no key and spends no API money.

Every execution requires an independently reviewed raw script hash, a pinned
source inventory and the pinned proposal, plus new absolute output paths.
The probe refuses changed pins or overlapping/existing outputs before creating
its fixture. It is not the live operator launcher; synthetic credentials and
authorization records provide no live spending permission.

Hosted checks are separate. At the recorded October 22, 23:19 UTC snapshot,

The proposed live source experiment remains **unallocated at $25 / 512
attempts**. No user command or key is needed for this completed rehearsal.
Its supplied programs, marker answers, canned groups/scores and synthetic usage
establish bounded engineering behavior; model authorship, task quality,
meaningful diversity, universal mutation competence and improvement of the
improver remain separate open gates.

## What remains a live observation

The gateway checks body bytes, selected profiles and output ceilings, then
checks reported usage. It does not pre-tokenize requests. Short supplied files
and synthetic usage counters cannot establish vendor context fit, an adequate
output-token allowance, account access, actual latency or actual cost. A live
truncation, rejection or incomplete run remains an explicit recorded outcome.
The worker wall limit bounds the isolated process. A host callback already
handling a provider request retains responsibility for its response and charge;
the worker limit is not an end-to-end host runtime guarantee.

The actual model-authored experiment, the universal mutation-competence gate,
changes to the improver, held-out improvement and improved-improver effectiveness
retain their separate completion gates. The rehearsal changes no official
NoveltyBench prompt, grouping, score, quality rule or summary formula.
