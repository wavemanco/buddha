# Fresh primary configuration preparation

The [standalone preparation recipe](conformance/prepare-fresh-primary.py) builds
a new, **unfunded** primary-comparison bundle. It reuses Buddha's existing
configuration validators. It does not start generation, judging or a search.
It creates no spending authority, run owner, runtime, approval, account review
or live-launch descriptor.

The proposed experiment keeps the frozen P/C source bytes, three development
tasks, 26 final tasks, seed 7, two starts, two development repetitions and two
descendant opportunities per arm. Its maximum final grid remains 312 sets.
The official NoveltyBench 1.1 instrument and registered analysis stay fixed.
The plain-model controls and review layers follow this primary preparation;
this recipe does not create them or change their scientific scope.

The recipe requires an independently reviewed input manifest and its exact
SHA-256 hash. The manifest names every permitted file. It separates metadata
inputs, archived component copies, current public Python sources and the 60
inherited custody references that may only be hashed. It grants no directory
scan of the old run. Databases, runtime-history trees, unknown input paths,
links and changed hashes are refused.

P/C programs are copied and hashed as bytes. They are not decoded, parsed,
imported, compiled or executed. Their hashes are also refused in metadata roles,
including renamed copies. Private custody evidence is hashed without parsing
or copying its contents. Retaining that evidence does not establish a fresh
exposure or task-separation judgment.
Checking those evidence bytes against a hash does not feed their contents to
the improver or return them in the reference record.

The new bundle contains copied data and components, current worker/helper
snapshots, relocated study and assessment declarations, the explicit reader
policy, the analysis inputs, an unfunded handoff and configuration checks.
The numerical check uses newly supplied synthetic rows through the existing
analysis API; it reads no old experiment scores and claims no scientific gain.
The reader policy is bound into primary controls before any later approval.

The destination must be new. Existing files are never overwritten. A failure
retains any new files and records its stage and safe reason where possible;
it does not retry, clean up or resume automatically. Named before/after hashes
check preservation; they do not establish an atomic filesystem snapshot.

The driver accepts `--inputs` for the reviewed manifest and `--sha256` for its
approved hash. Those flags prepare local files once and spend no model API
money. The recorded offline observation below has already been performed.
Another observation needs a new destination, exact reviewed inputs and its
own execution bound. Paid work needs the separate handoff described below.

Preparation does not transfer the old run's grants or outcomes. Paid work still
needs the comparable-size reader gate, complete ordinary-v2 composition,
prospective separation checks, current runtime and outgoing-request checks,
account/model/price/capacity checks, exact-source hosted verification and a
separately approved allocation and handoff. [PLAN.md](PLAN.md) remains the
scheduling authority; the construction-time choice remains separate.

For developers, this optional command runs only the supplied-data checks once
from the checkout containing this slice:

```powershell
python -m unittest discover -s tests -p test_fresh_primary_preparation.py -v
```

It uses temporary synthetic metadata, needs no API keys or Docker, spends no
API money and does not read the frozen experiment inputs. Use the current
PowerShell window; no separate window is needed. Wait for `OK`. Ctrl+C stops
it. The direct command has no enforced time limit; retained local observations
use their separately declared bound.
