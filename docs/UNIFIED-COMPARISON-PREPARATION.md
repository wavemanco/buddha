# One proposed budget for the Buddha study and plain references

The fresh configuration combines the original bounded improver study with two
same-model plain references. It is **unfunded, unadopted and not launchable**.
[PLAN.md](PLAN.md) remains the roadmap.

The study retains its original question: do the initial and evolved Buddha
improvers produce better descendants under the declared common conditions?
The plain references add another question: how do those frozen Buddha systems
compare with direct use of the same generator model? Compatible Buddha results
are reused for this comparison.

## Runtime checks and their limits

Four actual pinned containers completed 40 mocked generation requests on two
synthetic tasks per mode, then were removed. They used the prepared seed bytes,
selected request profile and executor settings: 256 MiB memory, one CPU, 64 PIDs,
64 MiB scratch and the 900-second wall limit. Temporary fixture mount paths and
synthetic wallet/task inputs differ from the future real run.

All requests used low effort and a 4,096-token output limit, without temperature,
top-p or extra system instructions. Independent histories had one message;
in-context histories grew from 1 to 19, retaining earlier answers and the
official continuation, then reset for the next task.

An initial rehearsal correctly stopped before HTTP because its existing tiny
synthetic authority could not cover the actual profile's reservation. A fresh
synthetic grant fixed the fixture; the real profile and budget guards were
unchanged. Both records are retained. Fake HTTPS, dummy keys and container
network isolation prevented provider access. No P/C program or private final
prompt ran in this proof. This closes the earlier 512-versus-256 MiB mismatch
for the synthetic generation rehearsal; it does not certify worst-case prompts,
provider latency, the complete native panel or performance.
