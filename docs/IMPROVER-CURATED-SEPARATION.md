# Curated preparation and improver separation

October 25, 2026. Bounded retrospective check for IMP-01, following the user's
choice to check Curated first. [PLAN.md](PLAN.md) remains the roadmap. The
[evidence record](conformance/imp01-curated-separation-review.json) identifies
the original files, checks and limits. This review makes no eligibility
declaration, creates no study and spends no API money.

## What the check found

**The recorded improver calls used development tasks only. No reserved-task
leak was demonstrated. The records still cannot certify the original 26-task
panel as unseen by the complete optimization process.** The missing part is
the history of host/source-author decisions, not the NoveltyBench judges.

| Boundary | Finding | What it establishes |
| --- | --- | --- |
| Prompt reviewers to preparation host | Two AI review contexts read all 100 Curated prompts before the split. They returned family maps, hashes, reasons and substantive task descriptions. Six retained preparation records match their original hashes. | Legitimate family preparation and a real return channel to the host. Reading prompts for this role does not automatically contaminate an experiment. |
| Preparation host to split/panel | The records show reconciliation of families, split assignment and development-panel selection. They declare no new outcome measurements for those decisions. | A documented preparation use. It does not establish every later use of the returned descriptions. |
| Frozen source to actual proposal calls | The three original P-to-W0, P-to-C and C-to-W1 requests contain feedback for `curated-0`, `curated-47` and `curated-97` only, with all thirty development answers. Literal request reconstruction matches the previously verified original request hashes. | Separation at these recorded callback boundaries. This check reconstructed requests without executing the selected source or querying the original ledgers. |
| Host/source author to agent changes | The complete historical author/root contexts and all out-of-band disclosures are not retained in these artifacts. | Unknown whether reserved-task descriptions influenced optimization decisions. Unknown does not mean a demonstrated leak, or permission to declare the panel eligible. |

The exact source composition also checks: P is the frozen seed, two newline
bytes and the full-output improver fragment. The old POL-02 policy matches the
earlier recovery-pilot policy, whose recorded creation predates the family
reviews. These facts close specific provenance questions; they cannot reveal
everything the later source author knew.

The original owners also bind the complete 100-task source and 26-task final
split as host controls. Those files are not mounted in the worker. The recorded
mounts contain only the agent and runner files; the callback contains the three
development tasks. A file's presence in host provenance is different from its
content reaching the improver.

## Why the remaining distinction matters

Suppose an improver never receives a reserved story prompt. If its author has
already used a description of that prompt to add a special story rule, the
test can still reward prior tuning. Checking just the final API request would
miss that path. This is an illustration of the risk, not a finding that it
happened here.

[DESIGN section 7](DESIGN.md#7-data-separation-and-valid-comparisons) covers
the whole optimization pipeline, including source authors' optimization
decisions, memory, retrieval and feedback. The trusted host is allowed to
read the complete source to verify it. The relevant distinction is preparation
or verification versus using reserved content to improve or select the agent.

The existing [custody check](VALIDATION-STUDY.md#task-custody-and-its-limits)
requires an evidence-backed declaration for a named optimization process.
It rejects selected tasks marked exposed or unknown. Naming only the isolated
workers would leave source-author decisions outside the claim; assigning a new
process name would not establish the missing separation. No such workaround
is adopted.

## What remains usable

Curated remains a valid official benchmark source. Its original scores and
all previous experiment records stay unchanged. It can support transparently
qualified development measurements without an unseen-task claim. This review
does not alter NoveltyBench's partitioning, utility calculation or judges.

The old 26-task final partition is disjoint from the known principal outcome
exposure and its declared family closure. That is useful evidence about those
records, not an exhaustive historical exposure audit or a custody certificate.
Neither a public dataset nor this review can establish what a base model saw
during training.

For the next strict sealed comparison, the remaining choice is:

- Prepare an entirely official WildChat development/final population with
  prospective role separation. Keep final prompt text and descriptive review
  notes with the data custodian; return only the IDs and non-descriptive family
  membership needed by optimization. Check existing exposure before assigning
  eligibility. WildChat is not presumed unseen merely because it is different.
- Use Curated for an explicitly qualified development comparison, preserving
  the missing historical-separation limitation. This would not close IMP-01's
  original sealed-task effectiveness requirement. It must not bypass the
  existing protected assessment's eligibility guard.

The first option is recommended for the next strict comparison because it can
establish the boundary prospectively. It changes the task population, not the
benchmark or Buddha's improvement mechanism. The user has not selected either
follow-up option yet; no new split, funding or launch is adopted here.

The generator and both judges still receive the current task when producing
or assessing answers. Eventual leaderboard submission still requires both
official subsets and the published generation protocol. Independent transfer
and human evaluation remain EVAL-02 requirements.

## Scope of this review

The review reads retained preparation records, frozen source as text, original
feedback and source/mount metadata. A separate reviewer traces the runtime
boundary; another checks the custody contract. The reconstructed request
hashes join prior raw-request evidence rather than claiming a fresh ledger
read. No selected source is imported, compiled or run, and no original owner
or ledger is written. All 451 files in the existing captured current-source
inventory remain byte-identical. This is a bounded information-flow review,
not a complete reconstruction of every historical conversation.
