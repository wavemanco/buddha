## Model limits and prices need separate treatment

The official OpenAI model Markdown pages specify a 1,050,000-token total context
and a separate 922,000-token maximum input for both configured models.
The saved 1,050,000 financial input ceiling is not a pre-send token count.
The existing original-call policy checks actual reply usage and context room;
its 32,768-token proposal allowance and 8,192-token context margin alone do not
establish the separate input maximum. [GPT-6.1 Sol documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol.md),
[GPT-5.6 Luna documentation](https://developers.openai.com/api/docs/models/gpt-5.6-luna.md).

The inspected Gateway reserves the financial maximum before dispatch and checks
reported usage afterward. It does not count input tokens before sending.
Source/feedback/wire byte ceilings are different limits. Lowering only the
financial ceiling would neither add that check nor preserve the closed capacity
policy. No oversized future request or provider rejection was observed here.
Retain this as a known limitation: a future request can be rejected for exceeding
the model's input limit. It is not evidence that any actual request was too large.

The next comparison will use the existing **original-call capacity observation**
mode allowed by [DESIGN §4](DESIGN.md#4-agent-interface-and-search-space), with
the unchanged policy required by study v4. Each actual proposal request and reply
is saved and checked before its returned child can run. A failed or unavailable
replacement stops the whole study as partial, preserving planned coverage,
stage, reason, costs and unresolved holds. Future requests have not passed in
advance. Full feedback, source identities and budget reservations stay intact.
An HTTP error or reply without usable billing information leaves an uncertain
charge and its reservation held. A reply with coherent usage can settle its
cost yet fail the replacement/capacity checks; that is recorded spending, not
an unresolved hold. Neither outcome permits the child to run. The controller
does not automatically reissue an uncertain original proposal operation.

This corrects the earlier readiness interpretation in revision 143: guaranteeing
acceptance of every future request before sending it is not required by this
mode. The financial ceiling remains a conservative charge bound under the
verified provider scope, rather than a token-fit certificate. Do not add a
counter, change endpoints, lower a cumulative output quota, truncate feedback or
repair the frozen actors solely to resolve this finding. The dated observations
and original capacity policy remain unchanged.

Fresh public price checks support the historical conservative token rates under
the stated processing scope, including the recorded cache/long-input/location
premiums. This is not a refreshed account-access check or a whole-run cost
estimate. Anthropic's standard service tier and standard speed are separate.
The later native-route review passes 12 pure checks: official scoring and refusal
fallback requests omit fast-mode opt-in, the gateway rejects its body/header
fields before dispatch, and the transport does not introduce them. This supports
the standard-speed request scope for this exact route. It does not attest to a
future returned bill; the current usage parser does not check `usage.speed`.
[Anthropic's explicit fast-mode opt-in](https://platform.claude.com/docs/en/build-with-claude/fast-mode).
[OpenAI pricing](https://developers.openai.com/api/docs/pricing),
[Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing).

OpenAI documents an input-count endpoint for Responses-format payloads. That

## Runtime and resource preparation

Read-only Docker metadata confirms the Linux daemon and both exact pinned images
are available, with the same runtime, environment and limits for both starts.
The images run as user 65532:65532. Generation has a 900-second worker limit;
native evaluation has 1,800 seconds. Availability does not prove worker isolation,
successful execution or that the full study will fit those limits.

The maximum declared grid contains 3,920 answer positions and 1,544 owners:
296 for development and 1,248 for final assessment. Owners are accounting and
evidence records, not one model call each. Broad local ceilings sum to
$29,300.000372; that is neither an expected bill nor a recommended allocation.

The current bridge permits one outstanding provider reservation per native
worker. The official concurrency setting does not double this host reservation.
The largest single quality-call reservation is $11.44. Before each next call,
its full reservation must fit **in addition to** money already committed, in
both its owner and phase. Failed/uncertain calls can retain holds. A small actual
bill does not mean the next call is affordable under the remaining cap.

For sensitivity only, one worksheet considers $50 development / 4,096 attempts
and $100 final / 12,288 attempts. These are **unadopted candidate caps**, not
approved funding or a request to the user. Under the specific hypothetical token
amounts below, all three sequences fit those caps and the unchanged local limits:

| Generation calls per ten-answer set | Hypothetical combined charge | Minimum development cap for that sequence | Minimum final cap for that sequence | Combined physical attempts |

| 1 | $87.875088 | $34.097350 | $76.325340 | 4,592 |

These are arithmetic examples, not measured or predicted token use. They assume

8,192/256 for planning, 16,384/6,144 for replacement, 8,192/512 for partition,
and 1,500/128 for utility. Output includes reasoning tokens. Larger inputs,
extra native passes, fallbacks or unresolved holds can exhaust a cap. The saved
medium and long sensitivity cases do not fit these candidate phase caps.
No aggregate configuration or preparation gate is adopted by this worksheet.

The earlier six-cell supplied-worker test took 1,196.174 seconds, including
bootstrap, deliberate tampering, replay and full-tree comparisons. It is not a
full-study runtime estimate. Source tracing finds repeated validation of growing
evidence prefixes. One separate synthetic diagnostic stopped within its

normal development was still unfinished after 221.6 seconds of observation.
Final assessment and passive inspection were not reached. The result is

That partial profile contains 1,422 tree scans, 883 capture finishes and about
5.42 million filesystem stat calls. It confirms substantial repeated host work
even without the earlier test's deliberate tampering and replay. Profiling adds
overhead and inclusive function times overlap; neither their sum nor this
prefix predicts full-grid duration. Retain the synthetic evidence and investigate
the narrow shared validation path before running a larger experiment. Application
source, integrity guards and paid records were unchanged; the existing fixture
supplied the worker transport. This was not an actual Docker or model run.
