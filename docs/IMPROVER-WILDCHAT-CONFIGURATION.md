## Model limits and prices need separate treatment

The official OpenAI model Markdown pages specify a 1,050,000-token total context
and a separate 922,000-token maximum input for both configured models.
The saved 1,050,000 financial input ceiling is not a pre-send token count.
The existing original-call policy checks actual reply usage and context room;
its 32,768-token proposal allowance and 8,192-token context margin alone do not
establish the separate input maximum. [GPT-6.1 Sol documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol.md),
[GPT-5.6 Luna documentation](https://developers.openai.com/api/docs/models/gpt-5.6-luna.md).

The inspected Gateway reserves the financial maximum before dispatch and checks
reported usage afterward. It does not count input tokens before sending.
Source/feedback/wire byte ceilings are different limits. Lowering only the
financial ceiling would neither add that check nor preserve the closed capacity
policy. No oversized future request or provider rejection was observed here.
Retain this as a known limitation: a future request can be rejected for exceeding
the model's input limit. It is not evidence that any actual request was too large.

The next comparison will use the existing **original-call capacity observation**
mode allowed by [DESIGN §4](DESIGN.md#4-agent-interface-and-search-space), with
the unchanged policy required by study v4. Each actual proposal request and reply
is saved and checked before its returned child can run. A failed or unavailable
replacement stops the whole study as partial, preserving planned coverage,
stage, reason, costs and unresolved holds. Future requests have not passed in
advance. Full feedback, source identities and budget reservations stay intact.
An HTTP error or reply without usable billing information leaves an uncertain
charge and its reservation held. A reply with coherent usage can settle its
cost yet fail the replacement/capacity checks; that is recorded spending, not
an unresolved hold. Neither outcome permits the child to run. The controller
does not automatically reissue an uncertain original proposal operation.

This corrects the earlier readiness interpretation in revision 143: guaranteeing
acceptance of every future request before sending it is not required by this
mode. The financial ceiling remains a conservative charge bound under the
verified provider scope, rather than a token-fit certificate. Do not add a
counter, change endpoints, lower a cumulative output quota, truncate feedback or
repair the frozen actors solely to resolve this finding. The dated observations
and original capacity policy remain unchanged.
